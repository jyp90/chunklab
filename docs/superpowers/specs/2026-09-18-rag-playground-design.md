# RAG 청킹/검색 비교 플레이그라운드 — 설계 스펙

- 날짜: 2026-09-18
- 상태: 승인된 설계 (구현 전)
- 작업 명칭(가칭): **chunklab** (후보: chunklab / ragmatrix / retrievelab — 런칭 전 도메인·PyPI 가용성 확인 후 확정)

## 1. 제품 정의

**"RAG 파이프라인의 A/B 테스트 플레이그라운드."**
문서와 테스트 쿼리를 넣으면 청킹 전략 × 임베딩 모델 × 검색 파라미터 조합을 매트릭스로 실행하고, 결과를 나란히 시각 비교하는 로컬 우선 개발자 도구.

### 타깃 사용자
- RAG 파이프라인을 구축 중인 개발자 (글로벌, 영어 UI/문서)
- 현재 청킹/임베딩 선택을 감이나 스프레드시트 수동 비교로 하고 있는 사람

### 핵심 가치 제안
1. 조합 비교를 수동 스크립트 대신 한 화면에서 (시각적 비교)
2. **문서와 API 키가 절대 외부 서버로 나가지 않음** (로컬 실행) — 핵심 세일즈 포인트
3. 설정 조합별 정량 메트릭(hit@k, MRR, NDCG) + 정성 확인(청크 프리뷰)을 동시에

### 경쟁 지형과 포지셔닝
- Langfuse/LangSmith: 프로덕션 관측/트레이싱 — 겹치지 않음 (개발 단계 도구로 포지셔닝)
- Ragas/DeepEval: 평가 라이브러리(코드) — 우리는 "보이는 도구"(UI)로 차별화
- 빈틈: 청킹/검색 설정 탐색 단계를 위한 시각적 비교 도구는 공백

## 2. MVP 범위

### 포함 (v1)
| 항목 | 내용 |
|---|---|
| 문서 입력 | md / txt / pdf 업로드 |
| 테스트 쿼리 | 수동 입력 + 선택적으로 정답 청크(golden chunk) 지정 |
| 청커 4종 | recursive, sentence-window, semantic, markdown-aware |
| 임베딩 3계열 | OpenAI, Gemini, sentence-transformers(로컬) |
| 파라미터 축 | chunk size, overlap, top-k, hybrid(BM25+dense) on/off |
| 메트릭 | hit@k, MRR, NDCG |
| 결과 화면 | 조합별 컬럼 나란히 비교 + 검색된 청크 원문 하이라이트 프리뷰 |
| 실행 방식 | `pip install chunklab` → `chunklab ui` → localhost:7860 |

### 제외 (v2 이후, YAGNI)
- 생성(answer) 품질 평가, LLM-as-judge
- 프로덕션 모니터링 / 트레이싱
- 평가 데이터셋 자동 생성
- 외부 벡터DB 연동 (Pinecone, Weaviate 등)
- 리랭커 비교

### 비교 화면 목업 (승인된 방향)
```
┌─ upload docs ──────────────────────┐
│ query: "what is the refund policy" │
├──────────┬──────────┬──────────────┤
│ recursive│ semantic │ sentence     │
│ 512/50   │ chunker  │ window       │
├──────────┼──────────┼──────────────┤
│ hit@5 ✓  │ hit@5 ✓  │ hit@5 ✗      │
│ 0.82     │ 0.91     │ 0.64         │
│ [chunk   │ [chunk   │ [chunk       │
│  preview]│ preview] │  preview]    │
└──────────┴──────────┴──────────────┘
```

## 3. 아키텍처

### 구성
- **단일 Python 패키지** (Python 3.11+, uv/ruff/ty — modern-python 스택)
- FastAPI 로컬 서버 + React 프론트엔드(빌드 산출물을 패키지에 정적 포함)
- 저장소: 로컬 SQLite (실험 설정·결과·이력)
- 벡터 검색: in-process numpy/FAISS — 실험 규모(문서 수십~수백 개)라 외부 벡터DB 불필요
- BM25: rank-bm25 또는 자체 구현 (hybrid 축용)
- 임베딩 API 키: 사용자 로컬 환경변수에서만 읽음

### 컴포넌트 경계
```
chunklab/
├── core/          # 청킹·임베딩·검색·메트릭 엔진 (UI 무관, 라이브러리로도 사용 가능)
│   ├── chunkers/    # 청커 4종, 공통 인터페이스: chunk(doc) -> list[Chunk]
│   ├── embedders/   # 임베딩 3계열, 공통 인터페이스: embed(texts) -> ndarray
│   ├── retrieval/   # dense / bm25 / hybrid 검색
│   ├── metrics/     # hit@k, MRR, NDCG
│   └── runner/      # 조합 매트릭스 실행, 결과를 JSON으로
├── server/        # FastAPI: 업로드, 실행 트리거, 결과 조회 API
├── ui/            # React 빌드 산출물 (정적)
└── cli/           # `chunklab ui`, `chunklab run --config x.yaml` (headless)
```

설계 원칙:
- core는 server 없이 단독 사용 가능 (CLI headless 실행 → JSON 출력). M1 산출물이자 CI 연동(유료 기능)의 기반
- 청커/임베더는 플러그인 인터페이스 — 추가가 쉬워야 커뮤니티 기여 유도 가능

### 데이터 흐름
1. 문서 업로드 → 로컬 저장
2. 실험 정의(조합 매트릭스) → runner가 조합별로 청킹→임베딩→인덱싱
3. 쿼리 실행 → 조합별 검색 결과 + 메트릭 계산
4. 결과를 SQLite에 저장, UI가 컬럼 비교로 렌더
5. 임베딩 결과는 (문서 해시, 청커 설정, 모델) 키로 캐시 — 조합 간 중복 임베딩 호출 방지 (API 비용 절감)

### 에러 처리
- 임베딩 API 실패: 조합 단위 부분 실패 허용 — 실패한 컬럼만 에러 표시, 나머지 결과는 정상 렌더
- PDF 파싱 실패: 해당 문서만 스킵하고 경고
- 대용량 문서: MVP에서는 문서당 크기 상한(예: 10MB)으로 단순화

### 클라우드 (2단계, MVP 이후)
- 결과 리포트 공유 링크, 실험 이력 저장, 팀 워크스페이스, CI 회귀 감지
- 로컬 결과 JSON만 push — 문서 원문은 로컬에 남김 (프라이버시 스토리 유지)
- MVP 런칭 반응 확인 후 착수. 스택 미정 (이 스펙 범위 밖)

## 6. 리스크

1. **무관심 (최대 리스크)**: "한 번 쓰고 끝" 도구가 되기 쉬움 → 이력/회귀 감지로 반복 사용 동기 설계. 런칭 반응이 수익화 가능성의 1차 검증
2. **프레임워크 내장화**: LangChain/LlamaIndex가 유사 기능 내장 가능 → 속도와 UX로 선점, 프레임워크 중립 포지셔닝
3. **이해충돌**: 범용 개발자 도구 + 개인 시간 + 개인 장비 전제. 회사 업무(학술 PDF, 한국 고전 텍스트, KRpia)와 코드·데이터·도메인 분리 유지. 취업규칙의 겸업/직무발명 조항은 본인이 직접 확인할 것
4. **API 비용**: 임베딩 호출은 사용자 부담(BYO key) — 서비스 원가에 포함되지 않음. 캐시로 사용자 비용도 최소화
